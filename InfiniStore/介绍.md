# InfiniStore 项目介绍

## 1. 项目定位

InfiniStore 是字节跳动开源的面向大语言模型（LLM）推理场景的分布式 KV Cache 存储与传输系统。

它主要解决 LLM 推理过程中 KV Cache 的存储、管理和跨节点传输问题。

需要明确的是：InfiniStore 负责 KV Cache 的存储和数据传输，不负责集群级别的 KV Cache 全局定位、路由和调度。

例如，集群中存在多个 InfiniStore Service，某个 Key 存储在哪个 Service 上，需要由上游服务判断。InfiniStore 不会主动查询其他 Service 来寻找这个 Key。

项目地址：[bytedance/InfiniStore](https://github.com/bytedance/InfiniStore?utm_source=chatgpt.com)

## 2. 整体架构

项目采用 Client-Server 架构，主要分为两个部分。

```
             上游调度服务
              Python 模拟
                   │
                   │ 确定 KV 所在位置
                   ▼
             InfiniStore Client
                   │
             选择目标 Service
                   │
          ┌────────┴────────┐
          │                 │
          ▼                 ▼
      Service 0         Service 1
          │                 │
       kv_map             kv_map
          │                 │
       LRU管理            LRU管理
          │                 │
       Memory Pool        Memory Pool
```

### 上游调度服务（Python）

负责模拟上游服务的调度和路由逻辑：

- 确定需要访问的 KV Cache。
    
- 判断 KV Cache 所在的 Service。
    
- 选择对应的 Client。
    
- 发起 KV Cache 读取和写入请求。
    

### InfiniStore（C++）

负责具体的 KV Cache 存储与传输：

- 接收 Client 请求。
    
- 管理本地 KV Cache。
    
- 根据 Key 查询 `kv_map`。
    
- 使用 LRU 管理缓存淘汰。
    
- 通过 RDMA 或 TCP 传输 KV 数据。
    
- 返回操作完成通知。
    

## 3. 网络通信架构

InfiniStore 支持两种数据传输路径：TCP 和 RDMA。

它们是两套不同的网络 I/O 处理机制，但最终使用 Service 管理的 KV 存储资源。

### TCP 路径

TCP 使用 libuv 事件驱动模型。

```
          TCP Client
               │
               ▼
          connect()
               │
               ▼
          TCP Server
               │
           uv_listen()
               │
               ▼
      on_new_connection()
               │
           uv_accept()
               │
          创建 client_t
               │
          uv_read_start()
               │
               ▼
            on_read()
               │
          解析 Header
               │
          解析 Body
               │
          handle_request()
               │
          tcp_payload_request()
               │
          ┌────┴────┐
          │         │
       TCP PUT   TCP GET
          │         │
          ▼         ▼
       写入 KV   查询 KV
          │         │
          └────┬────┘
               │
             ACK
```

主要函数：

|函数|作用|
|---|---|
|`register_server()`|初始化 TCP Server|
|`on_new_connection()`|接受新连接|
|`alloc_buffer()`|分配接收缓冲区|
|`on_read()`|接收和解析 TCP 数据|
|`handle_request()`|识别请求类型并分发|
|`tcp_payload_request()`|执行 TCP PUT / GET|
|`uv_write()`|异步发送数据|

TCP 使用连接复用模型，一个连接对应一个 `client_t`，同一连接可以处理多次请求，直到连接关闭。

### RDMA 路径

RDMA 使用 RDMA Verbs 进行远程内存访问。

```
          RDMA Client
               │
               ▼
          Service RQ
               │
               ▼
            RECV CQE
               │
               ▼
        cq_poll_handle()
               │
          解析 WC opcode
               │
          ┌────┴──────────┐
          │               │
       RECV CQE       READ/WRITE CQE
          │               │
       解析请求          完成处理
          │               │
       KV操作           更新状态
          │               │
       提交WR            ACK
          │
          ▼
        Service SQ
          │
          ▼
      RDMA READ/WRITE
          │
          ▼
       网卡执行
          │
          ▼
        产生 CQE
```

主要组成：

|组件|作用|
|---|---|
|RQ|接收 Client 发送的请求|
|CQ|接收 RDMA 操作完成事件|
|SQ|提交 RDMA SEND、READ、WRITE 等操作|
|CQ Poller|处理 CQ 完成事件|
|`kv_map`|管理 Key 与内存对象的映射|
|`lru_queue`|管理 KV 缓存淘汰顺序|
|Memory Pool|管理注册内存|

## 4. KV Cache 如何存储？

Service 使用 `kv_map` 和 LRU 管理 KV 数据。

```
              kv_map
                 │
          ┌──────┼──────┐
          │      │      │
        key_A  key_B  key_C
          │      │      │
          ▼      ▼      ▼
         PTR    PTR    PTR
          │      │      │
          ▼      ▼      ▼
       Memory Pool（注册内存）
```

其中：

- `kv_map`：保存 Key 到 PTR 智能指针的映射。
    
- `PTR`：管理实际 KV 数据所在的内存对象及其生命周期。
    
- `lru_queue`：记录 KV 的访问顺序，必要时淘汰较久未使用的数据。
    
- Memory Pool：提供 KV 数据的存储空间。
    

需要注意，`kv_map` 存储的是智能指针，不是直接存储 KV 数据本身。

## 6. 你目前的研究与改造

你目前主要研究的是 InfiniStore C++ Service 端的 RDMA 请求处理架构。

原本的设计：

- 一个 CQ Poller 处理不同类型的 CQE。
    
- 收到 RECV CQE 后解析请求、执行 KV 操作并提交 RDMA WR。
    
- 收到 RDMA READ/WRITE CQE 后处理完成事件、更新 KV 状态并提交 ACK。
    
- 请求接收、KV 管理、RDMA 提交和完成处理集中在一个 Poller 中。
    

改造后的设计：

采用 3 个 Poller、4 个软件队列的异步流水线架构。

|Poller|职责|
|---|---|
|CQ Poller|接收 CQE、识别事件类型、分发任务|
|KV Poller|KV 查询、内存管理、LRU 维护、完成后的 KV 状态更新|
|SQ Submit Poller|构造和提交 RDMA READ/WRITE WR、发送 ACK|

四个队列：

|队列|保存内容|
|---|---|
|`_recv_task_q`|新收到的请求元数据|
|`_rdma_submit_q`|等待提交的 RDMA READ/WRITE 任务|
|`_rdma_done_q`|已完成的 RDMA 操作及其关联任务|
|`_ack_q`|等待发送的 ACK 任务|

改造的目的，是将 CQ 事件处理、KV 业务逻辑和 RDMA 操作提交进行职责分离，降低业务逻辑对 CQ Poller 的占用。

## 7. 总结

InfiniStore 可以概括为三个层次：

1. 上游调度层：由 Python 模拟，负责判断 KV Cache 存储位置以及选择目标 Service。
    
2. 网络通信层：通过 TCP 和 RDMA 两种路径实现 Client 与 Service 之间的通信。
    
3. KV 存储层：通过 `kv_map`、LRU 和 Memory Pool 管理实际 KV Cache 数据。
    

你的改造主要针对第二层中的 RDMA 请求处理机制，通过多 Poller 和多队列实现异步任务解耦，并不涉及上游的 KV 全局路由和调度机制。
