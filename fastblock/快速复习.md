
# FastBlock 主要解决什么问题？

```
FastBlock 是一个基于 SPDK、RDMA 和 Multi-Raft 的高性能分布式块存储系统。

它主要针对传统分布式块存储在 NVMe SSD 场景下 CPU 开销较高、I/O 延迟较大、单卷性能不足等问题进行优化。

在存储层，使用 SPDK 用户态 NVMe 驱动和 Blobstore，减少内核 I/O 路径开销；在网络层，使用 RDMA 降低数据通信开销；在一致性层，通过 Multi-Raft 实现多副本日志复制与一致性。

整个系统主要由 Monitor、Client 和 OSD 三部分组成，分别负责集群元数据管理、I/O 请求发起以及实际的数据复制与持久化。
```

# 整个系统由哪些核心模块组成？例如 Monitor、OSD、Client 分别负责什么？

|模块|主要职责|
|---|---|
|Monitor|管理集群元数据，例如 OSDMap、PGMap、Pool、Image 信息，让 Client 和 OSD 知道集群拓扑和数据分布|
|Client|接收用户 I/O，根据 Object 定位 PG 和目标 OSD，发送 RPC 请求，处理响应、错误和重试|
|OSD|实际存储数据，管理 PG，借助 Multi-Raft 实现多副本一致性，通过 SPDK 完成底层存储 I/O|

面试时可以概括成一句话：

Monitor 管元数据，Client 负责请求路由，OSD 负责数据复制和存储。


# 为什么 FastBlock 要采用 Multi-Raft，而不是整个 OSD 集群只使用一个 Raft Group？

## 1.如果整个集群只有一个 Raft Group，

主要存在三个问题：

- Leader 瓶颈：所有写请求都经过同一个 Leader，它的 CPU、网络、日志处理能力可能成为整个集群的性能上限。
    
- 并行能力受限：所有写入共享一个 Raft 日志序列和提交进度，容易产生竞争。
    
- 扩展性差：增加 OSD 不一定提高写吞吐量，因为写请求仍然集中到同一个 Leader。

注意：单个 Raft Group 并不代表完全不能并发处理请求，而是所有请求共享同一个共识实例，扩展能力受到限制。

## 2.Multi-Raft 怎么解决？


```
第一，分散 Leader 负载。

不同 PG 的 Leader 可以分布在不同 OSD 上，而不是由一台 OSD 承担所有写请求。

第二，提高并行度。

每个 Raft Group 有自己的日志、Leader 和提交进度。

第三, 方便横向扩展。

随着 OSD 数量增加，可以通过调整 PG 分布和 Leader 布局，将工作负载分散到更多节点上。

不过，Multi-Raft 也有代价：Raft Group 越多，状态管理、心跳、内存和调度开销也越大。因此 PG 数量需要合理配置。
```

# OSD2 和 OSD3 如何选出新的 Leader？

```
Raft 选举的核心是：选举超时 → 发起投票 → 检查任期和日志 → 获得多数派 → 成为 Leader。

具体过程：

1. 检测 Leader 故障：OSD2 和 OSD3 长时间收不到 OSD1 的心跳，各自的选举计时器可能超时。
    
2. 发起选举：例如 OSD2 先超时，将自己的 Term 加 1，成为 Candidate，给其他节点发送 `RequestVote` RPC。
    
3. 检查投票条件：OSD3 收到请求后，检查候选者的 Term 是否有效、自己在该 Term 是否已投票，以及候选者的日志是否足够新。
    
4. 获得多数派：如果 OSD3 同意投票，OSD2 加上自己的一票，得到 2/3 的选票，就成为新 Leader。
```

# SPDK 相比传统 Linux `read/write` 有什么优势？

主要有三个方面：

① 用户态 I/O，减少内核开销

传统 `read/write` 通常需要系统调用，经过内核 I/O 路径。

SPDK 可以在用户态直接管理 NVMe 设备，减少系统调用、内核路径切换等开销。

② Polling 模型，减少中断开销

传统 I/O 经常采用中断通知完成。

SPDK 使用轮询方式检查 I/O 完成情况，避免频繁中断和线程唤醒带来的延迟。

③ 异步 I/O，提高并发能力

SPDK 提交 I/O 后不需要阻塞等待完成，可以继续处理其他请求。

这使它适合 NVMe SSD 这种高 IOPS、低延迟的存储设备。

# SPDK Reactor 和 SPDK Thread 有什么区别？

- Reactor：通常绑定一个 CPU Core，负责调度该 Core 上的 SPDK Thread。
- SPDK Thread：逻辑执行上下文，包含消息队列和 Poller，不一定对应一个独立的操作系统线程。
- Poller：注册在 SPDK Thread 上的周期性或持续执行的回调，用于推进具体任务。

所以要记住：

Reactor 是 CPU 调度层，SPDK Thread 是逻辑执行层，Poller 是任务执行机制。

# 为什么不用一个 RPC 对应一个线程？

你说线程内存开销大，这一点正确，但还可以补充：

- 每个 RPC 创建线程会增加线程栈内存开销。
- 大量线程会增加上下文切换和调度成本。
- Poller 配合异步 I/O，可以让少量线程管理大量并发请求。
- 通过消息传递让业务在指定 SPDK Thread 上执行，可以减少共享状态竞争。

需要注意：Poller 不等于一定减少所有中断。 对 SPDK NVMe 轮询模式而言，确实可以减少 I/O 完成中断开销；但在 FastBlock 中，Poller 还承担检查软件队列、推进状态机等职责。

# 为什么需要多个任务队列

因为一次 RPC 可能经历多个异步阶段，不能阻塞线程等待。

|队列|职责|
|---|---|
|`_task_list`|大 RPC 已收到元数据，等待发起 RDMA READ|
|`_read_task_list`|等待大 RPC 的数据读取完成|
|`_on_fligh_tasks`|已分发业务，等待 OSD / Raft 等操作完成|
|`_reply_task_list`|业务完成，等待发送 RPC 响应|

例如一个大写请求：

`_task_list → _read_task_list → _on_fligh_tasks → _reply_task_list`

这些队列让不同 Poller 分阶段推进任务。等待 RDMA 数据、Raft 多数派或者磁盘 I/O 时，线程仍然可以处理其他请求。
