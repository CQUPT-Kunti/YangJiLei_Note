# FastBlock

## PG 与 OSD 的理解

- PG 是一组 Object 的逻辑管理和放置单位。
    
- Object 会先根据映射规则计算出自己属于哪个 PG。
    
- PG 再对应一组 OSD，这些 OSD 负责保存该 PG 中 Object 的多个副本。
    
- 在 FastBlock 中，一个 PG 对应一个独立的 Raft Group。
    
- 一个 OSD 进程中会承载很多 PG 的本地实例。
    
- 同一个 PG 会在多个 OSD 中分别存在一个本地 PG 实例。
    
- 这些分布在不同 OSD 上的 PG 实例共同组成这个 PG 对应的 Raft Group。
    
- 每个 OSD 在不同 PG/Raft Group 中的角色可能不同：
    
    - 在某些 PG 中是 Leader
        
    - 在某些 PG 中是 Follower
        
    - 也有可能当前没有任何 PG 的 Leader 在这个 OSD 上
        

因此：

```text
不是：

PG 包含整个 OSD

也不是：

一个 OSD 包含整个 PG

而是：

一个逻辑 PG
    ↓
分布在多个 OSD 上
    ↓
每个 OSD 中都有这个 PG 的一个本地实例
    ↓
这些本地实例组成一个 Raft Group
```

---

## Object、PG、OSD 的关系

```text
Image
  │
  ▼
Object
  │
  │ 根据 Object ID 等信息计算
  ▼
PG
  │
  │ PG 的放置关系
  ▼
一组 OSD
```

例如：

```text
Object 123
    │
    ▼
  PG 1.3
    │
    ├─────────────┬─────────────┐
    ▼             ▼             ▼
  OSD1          OSD2          OSD3
```

如果 `PG 1.3` 是 3 副本，那么 Object 123 的数据会由这 3 个 OSD 中的 PG 1.3 实例共同维护。

# PG 架构

以 `PG 1.3` 为例：

```text
                    PG 1.3
                       │
        ┌──────────────┴──────────────┐
        │                             │
   Object 逻辑分组                Raft Group
        │                             │
   ┌────┼────┐             ┌─────────┼─────────┐
   │    │    │             │         │         │
 ObjA ObjB ObjC          OSD1      OSD2      OSD3
                         │         │         │
                     PG1.3实例  PG1.3实例  PG1.3实例
                         │         │         │
                      Leader    Follower   Follower
```

更详细：

```text
PG 1.3
│
├─ Object 集合
│   ├─ Object A
│   ├─ Object B
│   ├─ Object C
│   └─ ...
│
├─ Raft Group
│   │
│   ├─ OSD1
│   │   └─ PG 1.3 本地实例
│   │       └─ Raft Node：Leader
│   │
│   ├─ OSD2
│   │   └─ PG 1.3 本地实例
│   │       └─ Raft Node：Follower
│   │
│   └─ OSD3
│       └─ PG 1.3 本地实例
│           └─ Raft Node：Follower
│
├─ Raft Log
│   └─ 记录这个 PG 中发生的写入等操作
│
├─ State Machine
│   └─ Raft Log commit 后真正执行数据操作
│
└─ Object Data
    └─ 最终通过 Object Store / SPDK 保存
```

所以最重要的一句话：

> 一个 PG 是一个跨多个 OSD 的逻辑组；这些 OSD 中分别运行该 PG 的一个本地实例，而这些实例共同组成一个 Raft Group。

# OSD 架构

一个 OSD 是一个真正运行的存储服务进程。

一个 OSD 内部可能同时承载很多 PG：

```text
OSD1
│
├─ Monitor Client
│   ├─ 向 Monitor 注册
│   ├─ 获取 OSDMap
│   └─ 获取 PGMap
│
├─ RPC / RDMA
│   ├─ 接收 Client 请求
│   ├─ 与其他 OSD 通信
│   └─ 处理 Raft RPC
│
├─ PG Manager
│   │
│   ├─ PG 1.1 本地实例
│   │   └─ Raft Node：Leader
│   │
│   ├─ PG 1.2 本地实例
│   │   └─ Raft Node：Follower
│   │
│   ├─ PG 1.3 本地实例
│   │   └─ Raft Node：Follower
│   │
│   └─ PG 1.4 本地实例
│       └─ Raft Node：Leader
│
├─ Raft Log
│   └─ 保存各个 PG 的 Raft 日志
│
├─ State Machine
│   └─ commit 后执行真正的数据操作
│
├─ Object Store
│   └─ 保存用户 Object 数据
│
├─ KV Store
│   └─ 保存 Raft / OSD 内部元数据
│
└─ SPDK
    └─ 最终访问底层磁盘 / NVMe / AIO
```

# OSD 与多个 PG 的关系

例如有 3 个 OSD 和 3 个 PG：

```text
                 PG 1.1       PG 1.2       PG 1.3

OSD1             Leader        Follower      Follower
 │                 │              │             │
 ├─ PG1.1实例      │              │             │
 ├─ PG1.2实例      │              │             │
 └─ PG1.3实例      │              │             │


OSD2             Follower       Leader        Follower
 │
 ├─ PG1.1实例
 ├─ PG1.2实例
 └─ PG1.3实例


OSD3             Follower       Follower       Leader
 │
 ├─ PG1.1实例
 ├─ PG1.2实例
 └─ PG1.3实例
```

注意：

Leader/Follower 是针对某一个 PG 来说的。

不是：

```text
OSD1 = Leader
OSD2 = Follower
OSD3 = Follower
```

而应该说：

```text
对于 PG 1.1：
OSD1 = Leader
OSD2 = Follower
OSD3 = Follower

对于 PG 1.2：
OSD1 = Follower
OSD2 = Leader
OSD3 = Follower

对于 PG 1.3：
OSD1 = Follower
OSD2 = Follower
OSD3 = Leader
```

所以：

> 一个 OSD 可以同时是多个 PG 的 Leader，也可以同时是多个 PG 的 Follower。

# 一次 Object 写入时的关系

假设：

```text
Object 123
    ↓
PG 1.3
```

而：

```text
PG 1.3

OSD1 = Leader
OSD2 = Follower
OSD3 = Follower
```

那么写入流程可以理解为：

```text
Client
  │
  │ WRITE Object 123
  ▼
找到 Object 123 属于 PG 1.3
  │
  ▼
找到 PG 1.3 的 Leader
  │
  ▼
OSD1
  │
  └─ PG 1.3 本地实例
         │
         ▼
      Raft Leader
         │
         ├──────────────┐
         ▼              ▼
      OSD2            OSD3
   PG1.3 Follower   PG1.3 Follower
         │              │
         └──────┬───────┘
                ▼
             多数派确认
                │
                ▼
              commit
                │
                ▼
          State Machine
                │
                ▼
          Object Store
                │
                ▼
              SPDK
```

# 最终记忆方式

可以把 FastBlock 里的关系简单记成：

```text
Object
   ↓
属于某个 PG
   ↓
PG 对应一组 OSD
   ↓
每个 OSD 中都有这个 PG 的本地实例
   ↓
这些实例组成一个 Raft Group
   ↓
其中一个是 Leader
其他是 Follower
   ↓
Raft 保证副本一致
   ↓
State Machine 执行已经 commit 的操作
   ↓
Object Store 保存真正的用户数据
```

最核心的三句话：

> PG 是一组 Object 的逻辑管理和副本放置单位。

> 一个 PG 在多个 OSD 中都有本地实例，这些实例组成一个 Raft Group。

> OSD 是实际运行 PG、Raft、State Machine 和本地存储的存储进程。


## 任务执行

里面的工作线程都没有使用队列，都是使用的spdk里面的poller线程，每次都是进行的第一个任务。
而不是使用loop来进行，但是可以认为是loop，因为poller所在的线程每次都会进行循环


## 所有的日志和object存储其实都是使用的blob。
	只有 object 的 blob 是根据按需创建的，其他的比如raft log日志其实都是提前创建准备好的。
