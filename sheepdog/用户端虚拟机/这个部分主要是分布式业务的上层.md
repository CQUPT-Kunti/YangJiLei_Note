# guest 和 host

- **host（宿主机）**：跑 QEMU 进程和 KVM 的那台物理机。
- **guest（虚拟机）**：QEMU 创建出来的虚拟机，有独立的 vCPU、内存和虚拟设备。

## 1. 三者到底是什么

| 名称 | 是什么 | 作用 |
| ---- | ---- | ---- |
| Guest | 虚拟机（虚拟硬件 + guest OS） | 跑业务，产生块 I/O 请求 |
| QEMU | host 上的一个用户态进程（VMM） | 创建/管理虚拟机、提供虚拟设备、处理设备 I/O |
| KVM | Linux 内核模块（`/dev/kvm`） | 提供 CPU 硬件虚拟化能力，加速 guest 执行 |

**关键点：guest 不是独立进程，也不与 QEMU 同级。**

- guest 的每个 vCPU 是 QEMU 进程里的一个线程，靠 KVM 在 VMX/SVM 的 non-root 模式下直接执行 guest 代码。
- guest 的"物理内存"是 QEMU 进程 mmap 出来的一段地址空间，不是新分配的一台机器的内存。
- 所以准确说法是：**guest 跑在 QEMU 进程里面，QEMU 负责它的创建、管理和销毁**。

## 2. 一台 host 能跑多少台虚拟机

不是"64 核 ÷ 8 核 = 最多 8 台"这种硬上限：

- 8 vCPU 的虚拟机在 64 核机器上按 1:1 不超配算，是 8 台；但 vCPU 可以超配（例如 20 台 × 8 vCPU），只要不追求满载性能。
- 单台虚拟机也拿不到 vCPU 100% 的物理算力：KVM exit（I/O、中断、MMIO）、宿主调度、超线程争用、cache 抖动都会吃掉一部分。
- 实际更常见的瓶颈是**内存**（guest RAM 是 QEMU 进程实打实占用的内存）和 **I/O 带宽**，而不是核数。

# 一次写入里，哪些环节是"驱动"做的

以 QEMU + virtio-blk + sheepdog 为例，链路是：

```text
guest 内应用 write()
  └─ guest VFS → guest 文件系统 → guest 块层 → virtio-blk 前端驱动
       └─ 把请求写进 virtqueue（guest 内存里的环）+ kick 通知
            └─ QEMU virtio-blk 后端（取出请求）
                 └─ QEMU block layer → sheepdog 块驱动（block/sheepdog.c）
                      └─ 字节区间映射成 VDI 的 object（默认 4 MiB 一个）
                           └─ 网络发 object 请求到 sheep 集群
```

## 1. guest 侧：guest 内核自己完成

从应用 `write()` 到把请求放进 virtqueue，全程由 **guest 内核**完成，host 不参与：

- VFS → 文件系统 → 块层（bio）
- virtio-blk 前端驱动把 bio 变成 virtio 请求，写进 virtqueue，然后 kick（doorbell）通知后端

注意：**guest 侧产出的是块 I/O 请求（偏移 + 长度 + 数据），不是 object 请求**。guest 完全不知道 sheepdog 的存在，也不知道 VDI 和 object。

## 2. QEMU 侧：QEMU 的块驱动完成

- virtio-blk 后端从 virtqueue 取出请求（guest 的 kick 通过 eventfd 通知到 QEMU 的 vCPU 线程）
- 请求进入 QEMU block layer，落到 **sheepdog 块驱动** `block/sheepdog.c`
- sheepdog 驱动按 object 大小（4 MiB）把字节区间切开，oid 由 VDI id 和 object 序号拼成
- 以协程 + AIO 的方式把 `SD_OP_WRITE_OBJ`（新建时为 `SD_OP_CREATE_AND_WRITE_OBJ`）发到集群，收到应答后写回 guest 的 buffer，再以中断通知 guest

所以"从 virtqueue 取请求"和"生成 object 请求"这两步都在 QEMU 里，而且 **object 请求是 QEMU 的 sheepdog 驱动生成的**，不是 guest 生成的。

# sheepdog 怎么接进 QEMU：填一张表，做两跳转换

## 1. 接入 = 填满 QEMU 的 BlockDriver 表

QEMU 只认表不认人。表定义在 `include/block/block_int.h:87`，sheepdog 填在 `block/sheepdog.c:3220`：

| 字段 | 作用 | sheepdog 填的 |
| ---- | ---- | ---- |
| `.protocol_name` | 我叫什么 | `"sheepdog"` `:3222` |
| `.instance_size` | 私有状态大小 | `sizeof(BDRVSheepdogState)` `:3223` |
| `.bdrv_file_open` | 怎么打开我 | `sd_open` `:3225` |
| `.bdrv_co_writev` | 写 | `sd_co_writev` `:3239` |
| `.bdrv_co_readv` | 读 | `sd_co_readv` `:3238` |
| `.bdrv_co_flush_to_disk` | 刷 | `sd_co_flush_to_disk` `:3240` |

- 注册：`block_init(bdrv_sheepdog_init)`（`:3343`）
- 三份变体：`sheepdog` / `sheepdog+tcp` / `sheepdog+unix`（`:3220` / `:3259` / `:3298`）
- **这个文件在 QEMU 树里，不在 sheepdog 仓库**（版权 NTT，2009 年和 sheepdog 一起提交进 QEMU）

## 2. 两跳转换都在 QEMU 做，后端只收成品

```text
guest write → virtqueue
  ↓ 跳一  QEMU virtio-blk.c:614   描述符 → sector_num(:658) + qiov(:661)
  ↓ 跳二  QEMU sheepdog.c:2507    字节 → oid(:2522) + object 内 offset(:2509)
  ↓      以 struct sd_req 发出去
sheep/request.c:763 / :779   原样读进结构体，零转换 → plain_store 落盘
```

跳二本身只有三行：

```c
idx    = sector_num * 512 / object_size;                  /* :2508 第几个 object */
offset = sector_num * 512 % object_size;                  /* :2509 object 内偏移 */
oid    = vid_to_data_oid(inode->data_vdi_id[idx], idx);   /* :2522 */
```

## 3. FastBlock 也自己写了张表，只是填给 SPDK

`fastblock/src/bdev/bdev_fastblock.cc:689` 定义 `spdk_bdev_fn_table`（4 个回调），`:805` 用 `spdk_bdev_register` 注册。**和 sheepdog 完全同构，只是宿主程序从 QEMU 换成 `fastblock-vhost`。**

| | sheepdog | FastBlock |
| ---- | ---- | ---- |
| 填的表 | `BlockDriver`（QEMU 定义） | `spdk_bdev_fn_table`（SPDK 定义） |
| 注册函数 | `block_init` | `spdk_bdev_register` |
| QEMU 里的文件 | 有，3343 行 | **零** |
| 请求从哪来 | QEMU 调 `drv->bdrv_co_writev` | SPDK vhost 轮询 vring |
| 协议 / 能否跨机 | 私有 `SD_OP_*`、TCP，能跨机 | vhost-user、共享内存，必须同机 |

## 4. 一句话记住

**私有协议必须自带 QEMU 驱动**（sheepdog / nbd / rbd / iscsi），因为报文是私有的，总得有人在 QEMU 里翻译；
**公开协议不用**（vhost-user 系），QEMU 早有 `vhost-user-blk-pci` 通用前端，FastBlock 只需填 SPDK 的 bdev 表。
