# I/O 多路复用：select、poll、epoll

## 1. 它们是什么？

`select`、`poll`、`epoll` 统称为 **I/O 多路复用（I/O Multiplexing）机制**。

**作用：**一个线程同时等待多个文件描述符（fd，常见的是 socket）的 I/O 就绪事件，例如“可读”“可写”。它们负责**通知哪个 fd 可以进行 I/O**，而不是替程序执行 `recv()`。

## 2. 三者的主要区别

|对比|`select`|`poll`|`epoll`（Linux）|
|---|---|---|---|
|监听方式|每次传入 `fd_set` 位图|每次传入 `pollfd` 数组|先用 `epoll_ctl` 注册 fd|
|是否每次重新提供监听列表|**是**（`select` 会修改集合）|**要传数组**，但 `fd/events` 可复用|**不用**，内核保存注册关系|
|fd 数量限制|通常受 `FD_SETSIZE` 限制（常见 1024）|无固定的 1024 限制，受系统资源约束|受系统资源约束|
|如何找到就绪 fd|内核检查集合，应用再遍历|内核检查数组，应用再遍历|内核维护就绪事件，`epoll_wait` 返回就绪项|
|大量连接、少量活跃时|效率较低|效率较低|通常更高效|

> 注：`select/poll` 检查监听项的开销通常随监听数量增长；`epoll_wait` 取出就绪事件的开销主要与返回的就绪数量有关，不代表 epoll 的所有操作都是 O(1)。

## 3. 它们什么时候知道数据来了？会一直占用 CPU 吗？

1. 客户端发来数据，**Linux 内核网络协议栈**接收并放入对应 socket 的接收缓冲区。
2. socket 变为**可读**；内核通过等待队列或 epoll 的事件通知机制使等待者得到通知。
3. `select/poll`：内核检查监听的 fd，并返回就绪结果；`epoll`：内核维护就绪事件，`epoll_wait` 返回这些事件。
4. 程序再调用 `recv()` 读取数据。

**三者都可以阻塞等待，不会一直占用 CPU 询问。**

- `select`：超时参数为 `nullptr` → 可一直等；零超时 → 立即返回。
- `poll` / `epoll_wait`：超时参数 `-1` → 可一直等；`0` → 立即返回。
- 若在 `while` 中以 **0 超时**反复调用，才可能造成 **CPU 忙轮询**。

## 4. 餐厅类比

- **select**：服务员每次拿一份完整桌号名单检查；检查完名单被改动，下次要重做。
- **poll**：服务员每次拿同一张桌号表格检查；只更新“是否有订单”，表格可以复用。
- **epoll**：提前登记所有桌子，点餐系统记录哪些桌子有新订单；服务员直接取待处理订单。

三者在**没订单时都能休息（阻塞）**，并不是 select/poll 一直走来走去。

## 5. 哪种设计场景选哪一个？

|设计场景|推荐|为什么|
|---|---|---|
|**维护旧项目**，代码本来就在用 `select`|`select`|简单、改动小；连接很少时通常够用|
|**简单工具或小型服务器**，监听少量 fd|`select` 或 `poll`|二者都能满足要求；新写的类 Unix 代码通常更倾向 `poll`|
|**中小规模连接**，fd 数可能超过 `FD_SETSIZE`，希望代码相对简单|`poll`|没有 `select` 固定的位图大小限制，数组容易动态管理|
|**Linux 高并发网络服务器**，大量长连接、平时只有少数活跃|`epoll`|注册一次、反复等待；不用每次传输并检查整个 fd 集合|
|**Linux 聊天服务器、网关、反向代理、长连接服务**|通常 `epoll`|大量 socket 持续存在，连接活跃度变化大|
|**需要支持多个 Unix-like 系统**（不限 Linux）|`poll` 或平台抽象库|`epoll` 是 Linux 专有接口；其他系统可能使用 `kqueue` 等机制|

**选型口诀：** **少量连接 / 旧代码 → `select`；通用且需要灵活 fd 数组 → `poll`；Linux 大量并发长连接 → `epoll`。**

> 注意：没有“多少个连接一定要换 epoll”的统一门槛。还要看**同时活跃的连接数、每次等待的事件数、平台要求、开发维护成本**。连接很少时，三者的实际性能差别可能并不重要。

## 6. 一句话记忆

**select：位图、每次重建、有 fd 限制；poll：数组、可复用、仍需遍历；epoll：提前注册、内核维护就绪事件，适合大量并发连接。**

补充：**可读 ≠ 收到一条完整业务消息**；例如 TCP 是字节流，应用还需要处理粘包/拆包。
