# 互斥锁和自旋锁的区别

互斥锁（Mutex）和自旋锁（Spinlock）的核心区别在于：获取锁失败后，线程采用不同的等待策略，因此产生的 CPU 开销和线程调度开销不同。

## 1. 等待锁的策略

### （1）互斥锁：阻塞等待

当线程尝试获取互斥锁时：

- 锁空闲：直接获取锁，进入临界区。
- 锁被占用：线程可能进入阻塞状态，让出 CPU，由操作系统调度其他线程运行。
- 锁被释放：等待线程被唤醒，重新参与调度，尝试获取锁。

### （2）自旋锁：忙等待

当线程尝试获取自旋锁时：

- 锁空闲：直接获取锁。
- 锁被占用：线程不会主动进入睡眠，而是不断循环检查锁是否可用。
- 锁被释放：等待线程立即尝试获取锁并进入临界区。

## 2. 两者的开销区别

| 对比维度 | 互斥锁 | 自旋锁 |
| ---- | ---- | ---- |
| 获取失败后的策略 | 阻塞等待（可能先短暂自旋） | 循环忙等待 |
| CPU 开销 | 阻塞期间基本不占用 CPU | 持续消耗 CPU 时间 |
| 上下文切换 | 可能发生 | 通常不会因等待锁而主动切换 |
| 内核调度开销 | 可能较高 | 通常较低 |
| 缓存一致性开销 | 取决于实现和竞争情况 | 高频轮询可能产生额外开销 |
| 适用场景 | 临界区较长、锁竞争激烈 | 临界区极短、锁预计很快释放 |

# 为什么拷贝构造必须是引用

因为引用传参不需要构造新的 `A` 对象，也就不会再次调用拷贝构造函数，从而避免无限递归。

假设我们执行：

```cpp
A b = A(a);
```

如果拷贝构造函数是按值传参：

```cpp
A(A other);
```

那么执行过程是：

1. 构造 `b`，需要调用拷贝构造函数 `A(A other)`。
2. 因为 `other` 是值传递，所以需要先拷贝 `a`，构造一个新的形参对象 `A2`。
3. 构造 `A2` 又需要调用 `A(A other)`，因此必须先构造形参 `A3`。
4. 构造 `A3` 又需要构造 `A4`……形成无限递归依赖。

因此，拷贝构造函数必须使用引用：

```cpp
A(const A& other);
```

# 内存泄漏

内存泄漏是：分配内存，没有释放。

**常见场景**

1. `new` / `delete`，`malloc` / `free`
2. 异常安全漏洞，导致改变了执行流程跳过了，内存释放的代码
3. 释放责任不明确
4. 容器存储指针（出了容器不等于释放，触发出队列的时候明确有写）
5. 智能指针循环引用

其中第 3 点"释放责任不明确"是指：裸指针在函数之间、回调、线程之间传递时，没有约定由谁负责 `delete`。双方都以为对方会释放，就会泄漏；双方都释放，就会 double free。典型场景是构造函数接管裸指针、工厂函数返回裸指针，用 `unique_ptr` / `shared_ptr` 明确所有权即可避免。

前面三个可以使用智能指针进行解决，或者使用 RAII。

但是智能指针不是万能的。

泄漏排查使用 `valgrind`。

## 1. 原来的问题：shared_ptr 循环引用

```cpp
auto conn = std::make_shared<Connection>();

conn->set_callback([conn]() {
    conn->do_something();
});
```

为什么会循环引用？

- `conn` 是 `shared_ptr`，初始引用计数为 1。
- Lambda 使用 `[conn]`，复制 `shared_ptr`，引用计数 +1。
- `Connection` 保存 Lambda，而 Lambda 又持有 `Connection`。
- 即使外部 `conn` 被销毁，Lambda 仍然持有它，导致对象无法析构，造成内存泄漏。

## 2. 解决方案一：weak_ptr

核心：Lambda 使用弱引用，不增加强引用计数。

```cpp
auto conn = std::make_shared<Connection>();

conn->set_callback(
    [weak = std::weak_ptr<Connection>(conn)]() {
        if (auto ptr = weak.lock()) {
            ptr->do_something();
        }
    }
);
```

- `weak_ptr` 不增加强引用计数。
- `lock()` 成功时，临时增加 +1。
- `ptr` 析构后，引用计数 -1。
- 不会形成强引用循环。

## 3. 解决方案二：unordered_map

核心：Map 管理连接，Lambda 只捕获 ID，不捕获 `shared_ptr`。

```cpp
std::unordered_map<int, std::shared_ptr<Connection>> conn_map;

auto conn = std::make_shared<Connection>();
conn_map[100] = conn;

conn->set_callback([&conn_map, id = 100]() {
    auto it = conn_map.find(id);

    if (it != conn_map.end()) {
        auto ptr = it->second;
        ptr->do_something();
    }
});

// 外部不再持有
conn.reset();

// 连接关闭时移除
conn_map.erase(100);
```

- `conn_map` 持有 `shared_ptr`。
- Lambda 只捕获 Map 的引用和 ID，不复制 `conn`。
- `find()` 不增加引用计数。
- `auto ptr = it->second` 临时 +1。
- `conn_map.erase(100)` 释放 Map 持有的引用，没有其他强引用时对象析构。

注意：必须保证 Map 在回调执行期间有效，多线程访问时需要同步。

## 4. 常见引用计数操作

| 操作 | 强引用计数 | 原因 |
| ---- | ---- | ---- |
| `auto it = conn_map.find(id);` | 不变 | 只获取迭代器，没有复制 `shared_ptr` |
| `auto ptr = it->second;` | +1 | 复制 `shared_ptr`，增加一个所有者 |
| `auto& ptr = it->second;` | 不变 | 引用已有的 `shared_ptr`，没有复制 |
| `[conn]` | +1 | Lambda 按值捕获，复制 `shared_ptr` |
| `[&conn]` | 不变 | Lambda 按引用捕获，没有复制，但可能出现悬空引用 |
| `std::weak_ptr<Connection> weak = conn;` | 不变 | 创建弱引用，不增加强引用计数 |
| `auto ptr = weak.lock();` | 成功时 +1 | 对象存在时获取一个新的 `shared_ptr` |
| `conn.reset();` | 通常 -1 | 释放当前 `shared_ptr` 持有的强引用 |
| `conn_map.erase(id);` | 通常 -1 | 删除 Map 中的 `shared_ptr`，释放其持有的强引用 |

## 总结

循环引用的问题不在于引用计数临时 +1，而在于对象和它保存的 Lambda 相互持有强引用，导致计数始终无法归零。`weak_ptr` 和 Map 按 ID 查找都可以避免这种强引用循环。
