# 通过数据库理解块存储的使用方式

## 1. 数据库为什么需要块存储

数据库的核心任务是：

- 存储大量结构化数据
    
- 快速查询数据
    
- 高频修改数据
    
- 保证数据可靠性
    

例如一个用户表：

```text
user表

id     username     password     age
1      alice        xxx          20
2      bob          yyy          30
3      tom          zzz          25
```

数据库每天都会进行大量操作：

```text
查询用户
修改密码
更新订单状态
插入新数据
删除数据
```

这些操作不是简单地读取一个完整文件，而是不断定位某些数据位置，然后修改其中的一部分。

因此数据库需要一种：

- 可以随机读写
    
- 延迟低
    
- 数据可靠
    

的存储方式。

这就是块存储的使用场景。

---

# 2. 数据库看到的块存储是什么

数据库并不会直接看到 Ceph、云硬盘或者底层服务器。

数据库看到的是一个磁盘设备。

例如：

```text
/dev/vdb
```

整体结构：

```text
MySQL
 |
 |
数据库文件
 |
 |
文件系统(ext4/xfs)
 |
 |
块设备(/dev/vdb)
 |
 |
块存储系统
 |
 |
多个存储服务器
```

对于 MySQL 来说：

它认为：

> 我有一块硬盘，可以读写数据。

但实际上：

这块硬盘可能来自一个分布式存储集群。

---

# 3. 数据如何存入块存储

假设创建一个用户表：

```sql
CREATE TABLE user(
    id INT PRIMARY KEY,
    username VARCHAR(50),
    password VARCHAR(100)
);
```

插入数据：

```sql
INSERT INTO user VALUES
(1,'alice','123456');
```

过程：

## 第一步：数据库处理数据

MySQL InnoDB 不会直接保存成：

```text
alice
123456
```

而是组织成自己的数据结构：

```text
数据页(Page)

+----------------+
| id             |
| username       |
| password       |
+----------------+
```

InnoDB 默认 Page 大小：

```text
16KB
```

一个 Page 可以存很多条数据。

---

## 第二步：写入数据库文件

MySQL 会把 Page 写入数据文件。

例如：

```text
user.ibd
```

文件中的某个位置：

```text
Page 100
Page 101
Page 102
```

---

## 第三步：文件系统转换成块读写

文件系统看到：

```text
写入 user.ibd 某个位置
```

然后转换成：

```text
修改 Block 1000
修改 Block 1001
```

---

## 第四步：块存储保存数据

块存储收到：

```text
写入某几个块
```

然后保存：

```text
存储节点1
存储节点2
存储节点3
```

如果是 Ceph：

可能：

```text
数据

OSD1
 |
副本1

OSD2
 |
副本2

OSD3
 |
副本3
```

最终数据被可靠保存。

---

# 4. 查询数据时如何使用块存储

例如：

```sql
SELECT *
FROM user
WHERE id=100;
```

数据库不会扫描所有数据。

因为有主键索引。

流程：

```text
SQL查询
 |
 ↓
MySQL优化器
 |
 ↓
B+树索引
 |
 ↓
找到数据所在Page
 |
 ↓
读取Page
 |
 ↓
返回数据
```

例如：

B+树找到：

```text
id=100

位置：

Page 500
```

然后：

```text
读取Page 500
```

这个读取最终变成：

```text
读取块存储中的某些Block
```

---

# 5. 修改数据时块存储如何参与

例如：

用户修改密码：

```sql
UPDATE user
SET password='abcdef'
WHERE id=100;
```

过程：

## 1. 找数据

通过：

```text
id索引(B+树)
```

找到：

```text
Page 500
```

---

## 2. 修改内存

数据库通常不会立即修改磁盘。

先放入：

```text
Buffer Pool
```

例如：

```text
内存中的Page 500

password:

123456

↓

abcdef
```

---

## 3. 写日志

数据库先写：

```text
Redo Log
```

保证故障恢复。

例如：

```text
我要把password修改成abcdef
```

---

## 4. 刷回块存储

之后：

```text
内存Page
    |
    ↓
数据库文件
    |
    ↓
文件系统
    |
    ↓
块存储
```

最终持久化。

---

# 6. 为什么数据库不用对象存储

对象存储：

```text
图片.jpg
视频.mp4
backup.zip
```

特点：

- 大文件
    
- 顺序上传下载
    
- 不频繁修改
    

数据库：

```text
修改一个用户密码
修改一个订单状态
更新一个库存数量
```

特点：

- 小范围修改
    
- 高频修改
    
- 随机访问
    

例如：

修改：

```text
user id=100
```

数据库希望：

```text
直接定位数据位置
修改几个字节
```

而对象存储通常：

```text
读取整个对象
修改
重新上传
```

效率不适合。

---

# 7. 数据库使用块存储的优势

## 高随机IO性能

数据库大量：

```text
读取某个Page
修改某个Page
```

块存储可以快速定位。

---

## 数据可靠性

传统：

```text
服务器坏
 |
磁盘不可用
```

分布式块存储：

```text
数据副本

节点1
节点2
节点3
```

一个节点故障不会立即丢数据。

---

## 容量扩展

数据库增长：

原来：

```text
500GB
```

后来：

```text
5TB
```

块存储可以扩容：

```text
500GB
      ↓
5TB
```

数据库继续使用。

---

## 快照和备份

可以：

```text
数据库磁盘
      |
      ↓
创建快照
      |
      ↓
生成测试环境
```

例如：

生产数据库：

```text
订单库
```

复制：

```text
测试数据库
```

---

# 8. 一个完整架构示例

互联网公司的 MySQL：

```text
             应用服务

                |
                ↓

              MySQL

                |
                ↓

          InnoDB数据文件

                |
                ↓

          Linux文件系统

                |
                ↓

          云硬盘/ Ceph RBD

                |
                ↓

       分布式存储集群

                |
                ↓

      多台服务器 + 多块磁盘
```

---

# 9. 总结

数据库使用块存储的核心原因：

> 数据库需要一块高性能、可靠、支持随机读写的“虚拟硬盘”，而块存储正好提供这种能力。

整个过程：

```text
SQL请求
   ↓
数据库索引(B+树)
   ↓
找到数据Page
   ↓
读取/修改Page
   ↓
转换成文件读写
   ↓
转换成Block读写
   ↓
块存储保存数据
```

简单理解：

- 数据库负责管理数据结构
    
- B+树负责快速定位数据
    
- 文件系统负责管理文件
    
- 块存储负责提供可靠的磁盘能力
    

数据库并不知道底层有多少台服务器，它只认为自己拥有一块性能稳定的硬盘。
