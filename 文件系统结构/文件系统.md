# 文件系统基础

## 1. 文件系统到底在做什么？

文件系统最核心的事情可以理解成：

```text
路径 / 文件名
    ↓
找到文件记录
    ↓
找到磁盘数据位置
    ↓
读取真正的数据
```

Linux 常见：

```text
目录项 → inode → extent → 数据块
```

Windows NTFS：

```text
目录索引 → MFT Record → $DATA → cluster
```

---

## 2. 一个完整路径到底怎么找？

假设 Linux 有：

```text
/ak/ac/fg/你好.jpg
```

假设：

```text
/        inode 2
ak       inode 100
ac       inode 200
fg       inode 300
你好.jpg  inode 500
```

系统先拿到根目录 inode：

```text
inode 2
```

inode 2 告诉系统：

```text
我是目录
我的目录数据在这些 block
```

读取目录数据：

```text
ak  → inode 100
tmp → inode 20
etc → inode 30
```

于是找到：

```text
ak → inode 100
```

继续读取 inode 100：

```text
inode 100
类型：目录
目录数据位置：block 700
```

block 700：

```text
ac → inode 200
```

继续：

```text
inode 200
↓
目录数据
↓
fg → inode 300
```

再继续：

```text
inode 300
↓
目录数据
↓
你好.jpg → inode 500
```

最终：

```text
inode 500
类型：普通文件
大小：5MB
extent：block 8000~9279
```

读取真正数据。

完整过程：

```text
根 inode
   ↓
目录数据
   ↓
ak → inode 100
   ↓
目录数据
   ↓
ac → inode 200
   ↓
目录数据
   ↓
fg → inode 300
   ↓
目录数据
   ↓
你好.jpg → inode 500
   ↓
extent
   ↓
文件数据
```

所以：

> 目录 inode 指向的“数据块”，里面主要是目录项；普通文件 inode 指向的数据块，里面才是真正的文件内容。

## 3. inode 表是不是一棵树？

不是。

ext4 的 inode 表更接近固定大小记录组成的数组：

```text
inode table

inode 1
inode 2
inode 3
...
inode 500
...
```

拿到：

```text
inode = 500
```

系统可以根据 inode 编号直接计算它在 inode table 中的位置。

所以：

```text
inode编号 → inode
```

通常不是 B+树搜索，而是类似：

```text
inode_table[500]
```

inode 表当然不是无限大的。

文件系统创建时会规划 inode 数量，并且 ext4 又把磁盘分成多个 block group，每个 block group 都有自己的 inode table。

## 4. 为什么还需要 Hash / B+树？

因为真正麻烦的是：

```text
文件名 → inode/MFT编号
```

例如一个目录有：

```text
50万个文件
```

如果一个一个扫描：

```text
a.txt
b.txt
c.txt
...
你好.jpg
```

会很慢。

所以目录内部需要索引。

Windows NTFS：

```text
父目录
  ↓
B-tree / B+tree 风格目录索引
  ↓
文件名
  ↓
MFT Record
```

详见：

[02-Windows-NTFS.md](https://chatgpt.com/c/02-Windows-NTFS.md)

Linux ext4：

```text
父目录 inode
  ↓
HTree
  ↓
文件名 hash
  ↓
directory entry
  ↓
inode
```

详见：

[03-Linux-ext4.md](https://chatgpt.com/c/03-Linux-ext4.md)

## 5. 已知完整路径和只知道文件名，是两回事

### 已知完整路径

例如：

```text
/ak/ac/fg/你好.jpg
```

系统知道每一级要找什么：

```text
/ 中查 ak
↓
ak 中查 ac
↓
ac 中查 fg
↓
fg 中查 你好.jpg
```

这是路径解析。

### 只知道文件名

例如只知道：

```text
你好.jpg
```

不知道它在哪。

文件系统的“目录索引”不能直接全盘找到它。

因为：

```text
/a 目录有自己的索引
/b 目录有自己的索引
/c 目录也有自己的索引
```

不存在一个 ext4 HTree：

```text
整个磁盘：
你好.jpg → inode 500
```

所以如果没有额外搜索索引，就需要遍历目录树。

例如：

```bash
find / -name "你好.jpg"
```

本质上会递归检查目录。

很多桌面搜索软件之所以非常快，是因为它们另外建立了：

```text
全局搜索数据库
```

例如：

```text
你好.jpg → /a/b/c/d/你好.jpg
```

这和文件系统本身的目录索引不是一个东西。

## 6. 我之前容易混淆的问题

### inode 的数据块里面是不是保存下一个 inode？

如果 inode 是目录：

```text
是间接意义上的。
```

目录数据块保存：

```text
名字 → inode编号
```

例如：

```text
fg目录：

你好.jpg → inode 500
```

然后再去 inode table 找 inode 500。

如果 inode 是普通文件：

```text
数据块就是文件内容。
```

---

### B+树是不是通过“文件大小”比较？

不是。

B+树比较的是：

```text
key
```

key 可以是：

```text
数字
字符串
时间
文件名
```

文件名虽然是字符串，也可以定义排序关系。

---

### 中文文件名怎么办？

中文同样是 Unicode 字符串。

索引只需要能回答：

```text
字符串 A < 字符串 B？
```

并不需要理解中文含义。

## 7. 最后记住

```text
路径解析：
一级目录 → 下一级 inode/MFT → 再下一级
```

```text
目录索引：
在“已经确定的父目录”中快速找某个名字
```

```text
inode/MFT：
告诉系统文件是什么、属性是什么、数据在哪里
```

```text
搜索软件：
可能另外维护一个全局文件搜索数据库
```
